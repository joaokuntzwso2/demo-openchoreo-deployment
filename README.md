# OpenChoreo Platform Application Demo

A complete local platform demonstration built on **OpenChoreo v1.2.2**, k3d and Docker. It combines two application domains, live Kubernetes operations, governed platform abstractions, observability, MCP-based agent tooling and Rancher cluster management in one reproducible package.

## What you get

- **Unified Platform Portal** — polished launcher and scenario console.
- **Financial Services Experience** — customer context, payment orchestration, fraud, compliance and a managed Valkey resource.
- **Financial Operations Agent** — MCP tool discovery across OpenChoreo, customer, risk and compliance services; works in scripted mode without an LLM key.
- **Telecom Operations Experience** — subscriber/BSS, network assurance, 5G QoD, partner commercial wallet, central policy, legacy SOAP modernization and governed MCP tools.
- **Kubernetes Operations Console** — runs inside the OpenChoreo data plane and reads the real Kubernetes API to show Pods, Deployments, Services, HTTPRoutes, NetworkPolicies, Events and OpenChoreo CRs. It includes controlled restart/delete-pod actions restricted to the demo namespaces.
- **Rancher** — starts as a local Docker container and the bootstrap attempts to register the existing OpenChoreo k3d cluster automatically.
- **Containerized alert receiver** — a small Dockerized webhook sink on port `18081` captures alert evidence from the OpenChoreo observability plane.
- **Clean-room verification** — the run is not considered successful until the acceptance suite verifies OpenChoreo cells, images, Components, Releases, application flows and Kubernetes visibility.

## Architecture at a glance

The package creates **10 OpenChoreo Projects**, **30 ProjectReleaseBindings** (development/staging/production) and **19 application Components**. Application workloads run in the OpenChoreo-managed Kubernetes data plane. Rancher is intentionally outside that cluster so it can act as a cluster-management view.

## Workstation requirements

Recommended for macOS/Colima:

- Docker-compatible runtime / Colima
- k3d
- kubectl
- Helm
- curl
- Python 3
- Node.js is optional on the host; when present it enables the fast source-level integration preflight. Runtime services are containerized.
- **6 CPU / 16 GiB Docker VM memory recommended** (12 GiB minimum with Rancher enabled)
- at least **25 GiB free Docker VM disk** before a clean build

Apple Silicon recommendation:

```bash
colima start --vm-type=vz --vz-rosetta --cpu 6 --memory 16
```

## Run from a fresh clone or extracted ZIP

```bash
chmod +x demo.sh scripts/*.sh
./scripts/self-test.sh
./demo.sh up
```

`./demo.sh up` is idempotent. It installs/reconciles the platform and then runs the strict verifier.

For the strongest reproducibility proof:

```bash
./demo.sh reset | tee /tmp/openchoreo-platform-clean-room.log
```

`reset` deletes only this demo's k3d cluster, Rancher container/volume, runtime files and `platform-demo/*` application image tags, then rebuilds the entire environment with no-cache application image builds.

Success markers:

```text
==> CLEAN-ROOM CORE VERIFICATION PASSED
==> FULL CLEAN-ROOM RUN PASSED
```

To make Rancher registration part of the acceptance gate as well:

```bash
RANCHER_REQUIRED=1 ./demo.sh reset | tee /tmp/openchoreo-platform-clean-room.log
```

That mode waits for the Rancher server and the downstream `cattle-cluster-agent` inside the OpenChoreo k3d cluster before declaring the run complete.

## URLs

The bootstrap prints the resolved OpenChoreo external URLs at the end. Standard local management URLs are:

- OpenChoreo: `http://openchoreo.localhost:8080`
- Rancher: `https://localhost:8444`
- Rancher user: `admin`
- Rancher image: `rancher/rancher:latest` by default (override with `RANCHER_IMAGE`)
- Rancher bootstrap password: generated locally on first start and stored under the ignored `runtime/` directory. You can override it with `RANCHER_BOOTSTRAP_PASSWORD`.

Typical application routes use the host `development-platform-demo.openchoreoapis.localhost:19080` with a per-component path. Use `./demo.sh status` to print the exact paths generated by OpenChoreo.

## Lifecycle

```bash
./demo.sh up       # install/reconcile + verify
./demo.sh reset    # destructive clean-room rebuild + verify
./demo.sh verify   # strict end-to-end verification
./demo.sh status   # status and all external URLs
./demo.sh rancher  # start/retry Rancher registration
./demo.sh scenario help # list presenter-ready scenarios
./demo.sh stop     # stop cluster + Rancher + local webhook
./demo.sh start    # restart stopped environment
./demo.sh destroy  # delete this demo cluster and Rancher data
```

## Recommended demo flow

1. Open the **Platform Portal** and show overall runtime health.
2. Run a normal financial payment, then a fraud challenge or compliance hold.
3. Open OpenChoreo and show the cross-project dependencies and managed cache.
4. Run a 5G Quality-on-Demand telecom scenario and a data-residency policy denial.
5. Show the legacy BSS SOAP-to-REST transformation.
6. Open the **Kubernetes Operations Console** and correlate the business flow with real Deployments, Pods, Services, HTTPRoutes and NetworkPolicies. Restart one demo Deployment and watch Kubernetes converge.
7. Open **Rancher** and show the same k3d/OpenChoreo cluster from a cluster-management perspective.

## Telecom adaptation

The telecom domain is an OpenChoreo-native adaptation of the runtime concepts in:

`https://github.com/joaokuntzwso2/demo-apim-telco-environment`

The original repository demonstrates WSO2 API Manager / Micro Integrator capabilities around telco/Open Gateway scenarios. This package moves the underlying demo domain services into OpenChoreo Components so they are directly visible in Kubernetes. The full APIM/MI product layer is intentionally not part of the default laptop bootstrap; see `docs/TELCO-OPENCHOREO-ADAPTATION.md`.
